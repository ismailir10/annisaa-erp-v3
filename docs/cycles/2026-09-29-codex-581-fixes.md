# Codex review fixes on the 2026-09-29 promotion (#581)

## Context

Codex reviewed promotion PR #581 (staging → main) and raised two findings in code merged earlier that day. Both reproduce:

- **P1: rate-limit the payment reversal endpoint** (`app/api/invoices/[id]/payments/[paymentId]/reverse/route.ts`, added in #579). `.claude/standards/security.md` requires `rateLimit()` on every write endpoint. This route opens an advisory-lock transaction on the invoice with no limit, so one `payments.record` principal can queue unbounded serialized transactions on an invoice.
- **P2: re-read primary status inside the transaction** (`lib/guardians/primary.ts`, added in #574/#580). Both guardian status routes read `guardian.isPrimary` before calling `changeGuardianLinkStatus`, and the helper reused that value, including on its P2034 retry. Concurrent deactivations can go wrong:
  1. Request A deactivates G1 and promotes G2.
  2. Request B then deactivates G2 using its stale `wasPrimary=false`.
  3. B skips promotion, and the remaining ACTIVE guardian G3 is left with no primary.

  A student with no primary guardian gets invoices and payment links with no recipient: the CORE-4 bug this helper exists to prevent.

## Spec

- [x] The reversal route returns 429 after 20 reversals per user per minute. The check runs before body parsing and before any transaction opens. Copy is Indonesian and follows the existing 429 messages.
- [x] `changeGuardianLinkStatus` reads the target link's `isPrimary` inside every transaction attempt. The `wasPrimary` argument is removed, so no caller can pass a stale value, and both routes are updated.
- [x] Regression tests fail before the fix and pass after.

Non-goals: rate limits on other finance routes (the record-payment route also has none, and is out of this PR's scope; queued as a follow-up), and any schema change.

## Implementation

- Subagent plan: inline, no fan-out. Two small local fixes in files already read while verifying the findings; a subagent would re-read the same four files.
- Task 1: `reverse/route.ts` calls `rateLimit(\`reverse-payment:${session.id}\`, 20, 60_000)` right after the permission check. Test: `app/api/__tests__/invoice-payment-reverse.test.ts`, "429 after 20 reversals…".
- Task 2: `lib/guardians/primary.ts` does `tx.studentGuardian.findUnique({ select: { isPrimary } })` at the top of the INACTIVE branch and drops `wasPrimary` from the args. `app/api/guardians/[id]/route.ts` and `app/api/students/[id]/guardians/[guardianId]/route.ts` stop passing it. Tests in `lib/guardians/__tests__/primary.test.ts`:
  - the link became primary after the route read it, so a replacement is promoted;
  - deactivating a non-primary promotes nobody;
  - the P2034 retry re-reads `isPrimary` instead of reusing the first attempt's view.
