# Codex review fixes on the 2026-09-29 promotion (#581), round 2

## Context

Codex left six findings on promotion PR #581 (staging → main). Two were fixed in #583 (`docs/cycles/2026-09-29-codex-581-fixes.md`). This session only received notifications for those two; the other four were found when reading the review threads before resolving them. All four are in code merged earlier on 2026-09-29, and each was checked against the code before fixing.

- **P1 salary clear** (`components/admin/employees/salary-editor.tsx`, from #580 HR-3):
  - The editor dropped cleared components from the PUT payload, and the route only upserts, so the old `EmployeeSalaryValue` stayed. After the success toast and refetch the amount came back, and payroll kept paying or deducting it.
  - Sending 0 is not the fix. Payroll's generate route warns "Belum ada struktur gaji" only when an employee has no salary rows, and 0 still counts as a row. The editor also shows "Belum diatur" for no row versus "0" for zero.
- **P1 restore re-enables admin logins** (`app/api/employees/[id]/restore/route.ts`, from #573 HR-4):
  - Restore set every linked INACTIVE user to ACTIVE with only `employees.edit`. That includes SCHOOL_ADMIN and SUPER_ADMIN logins disabled separately on the users page.
  - `PUT /api/users/[id]` requires `users.edit`, and a SUPER_ADMIN actor for SUPER_ADMIN targets. Restore bypassed both.
  - Mirror image found while verifying: deactivate could disable a SCHOOL_ADMIN login with only `employees.edit`.
- **P1 stacked overlay** (`components/student-journal/note-compose-dialog.tsx`, from #578 T3):
  - The "Buang catatan?" guard mounted a `ConfirmDialog` (AlertDialog) over the open composer Dialog/Sheet.
  - `.claude/standards/ui.md` Overlays Rule: "One overlay at a time … Close the current overlay before opening another." The same section also says confirms always go through `<ConfirmDialog>`, so this case was ambiguous.
- **P2 paidAt overwritten** (`lib/finance/invoice-payment-state.ts`, from #579 FIN-6):
  - `deriveInvoicePaymentState` stamped `paidAt = new Date()` whenever the result was PAID. The webhook accepts overpayment, so reversing a manual payment on an overpaid invoice that stays covered rewrote the settlement date.
  - That date is shown to parents ("Dibayar <date>"), printed on the receipt PDF and used in parent activity.
  - The record route and webhook are not affected: they never recompute an already-PAID invoice.

## Spec

- [x] Clearing a stored salary component sends `value: null`, and the API deletes that row. 0 stays a real, upserted value. Components not in the payload are untouched.
- [x] Deactivate and restore change a linked login only when the actor could do the same on the users page (`mayToggleLinkedLogin`):
  - SUPER_ADMIN logins: only by a SUPER_ADMIN actor.
  - SCHOOL_ADMIN logins: only with `users.edit`.
  - Everyone else follows the employee, as in HR-4.
  - The employee row itself is always updated.
- [x] The composer asks "Buang catatan?" in its own footer: an inline row with `role="alert"` and focus on "Lanjut menulis". While it is showing, Escape or an outside tap means keep writing. There is no second overlay, and `ui.md` now states this pattern.
- [x] A PAID invoice that stays PAID keeps its `paidAt`. It falls back to now only when missing. An invoice crossing into PAID gets a fresh stamp.
- [x] Each fix has a test that fails before it and passes after.

Non-goals: a schema marker for "disabled by employee deactivation" (not possible without a migration; the role rule closes the escalation without one), and other stacked `ConfirmDialog` uses (`add-teacher-dialog`, `keringanan-tab`, `leave-sheet`), which are older, not in #581, and are not dirty-form guards.
